# Release — theory

> What a shippable, reproducible Android release IS and why. The QUALITY-BAR §7 path to the store.
> How, per stack: `../lib/android/reference/release-impl.md`. Anchored to [QUALITY-BAR](../QUALITY-BAR.md) §7, §8.
> Read one Term via `section-query`: Grep `^## <Term>` → Read(offset, limit=N).

A release is **one reproducible artifact that ships to real users** (QUALITY-BAR §7): the same source and inputs produce the same signed App Bundle, minified and optimized, with a keystore that never left the CI secrets. Everything below is the discipline that makes "press release" a non-event instead of a nerve-racking ritual — [Gradle build](https://developer.android.com/build) docs are the authority.

## Versioning <!-- 3 -->
Every release carries **both a visible version and a monotonic machine version** (QUALITY-BAR §7): user-facing SemVer (`1.2.0`) plus a strictly increasing `versionCode` that the store and devices compare. A duplicate or zeroed `versionCode` is a release that silently fails to install over the previous one. Versioning is automated at release time — "what version is this build?" must always have a one-word answer in `about`, CI, and crash reports.

## Build Variants <!-- 3 -->
**Debug and release are distinct, unforgivable pipelines** (QUALITY-BAR §7): debug is fast and debuggable and never ships; release is minified, shrink-wrapped, non-debuggable, with its own signing and resources. The defect pattern — "it worked in debug" — is the artifact of a release tree that drifted from the debug tree. A release build's only job is to be *the* production thing; it is exercised by an automated release-jar sanity pass, not by hope.

## Minification & R8 <!-- 3 -->
Release runs **R8: shrinking, obfuscation, optimization** (QUALITY-BAR §7) — the difference between a lean APK and a bloated one, and the enforcement that reflection-heavy libraries (Hilt, Room, Retrofit) stay wired via keep rules rather than by default. R8 is not an optional performance step: a release without it ships unused code. Rules are maintained next to the library that needs them, reviewed like code.

## Keep Rules <!-- 3 -->
R8's escape hatches — **`keep`/`keepnames` rules — are explicit and minimal** (QUALITY-BAR §7): kept entries are the load-bearing reflection points (DI-generated code, serializers, configured libraries), never a keep-everything fallback. An over-kept release silently forfeits its shrinking. Rule hygiene pays as crash-free stability: the classic shape is "worked in debug, class-not-found at release" — verified by an instrumented smoke run against the *released* artifact.

## App Bundle (AAB) <!-- 3 -->
**The shipped artifact is an App Bundle** (QUALITY-BAR §7): device-targeted APKs generated by the store (language, density, ABI) instead of one universal APK — a smaller download for everyone. AAB is the qualified delivery format for Play; the pipeline's artifact is the bundle, and the base APK it expands to is what smoke tests run against. For an agent: build the APK to debug; build the AAB to ship.

## Signing <!-- 3 -->
Release builds are **signed with a keystore that exists only in the CI secret store** (QUALITY-BAR §7): never in VCS, never in `build.gradle`, never in a console history. The keystore is the app's permanent identity — losing it means a new identity and stranded updates; leaking it means forged updates. Signing is verified in CI on the artifact itself, and debug signing never crosses into the release job.

## Version Catalogs <!-- 3 -->
Dependency and plugin versions live **centrally, bumped deliberately** (QUALITY-BAR §7): one catalog file reviewed like code, driven by Dependabot/Renovate, with the CI gates re-run per bump. A catalog is what turns "a dependency moved" into a visible reviewable change where a mid-buildscript bump is invisible history. Bumps flow through the pipeline *as changes*, not as fire-and-forget mutations.

## Reproducible Builds <!-- 3 -->
The same tag produces **the same artifact outputs** (QUALITY-BAR §7): deterministic ordering and input hashing, a build that does not depend on the machine or the day it ran. Without it, "which build is in production?" becomes a forensic question. A build whose output can drift silently is a release-story defect hiding in plain sight.

## Baseline Profile in Release <!-- 3 -->
The shipped release **carries a regenerated baseline profile** (QUALITY-BAR §5, §7): profiles shipped with the bundle precompile the app's hot paths at install time — where cold-start and jank guarantees actually land on real devices. Profiles expire against a moving codebase, so they are regenerated per release, never shipped once and forgotten (performance-theory).

## CI Pipeline <!-- 3 -->
The pipeline is a **sequence of gated jobs**: lint → static analysis → unit tests → build → artifact smoke, with instrumented/Compose tests on an emulator as a separate job (QUALITY-BAR §8). Each gate is blocking and cheap, and failures name the standard broken rather than just "build failed". A release pipeline adds signing/minify/verify on a protected-tag pass — same discipline, different key.

## Artifact Verification <!-- 3 -->
The released artifact is **checked, not assumed** (QUALITY-BAR §7): signature verified, version rendered and matched to the tag, minified-R8 rules crash-free in an instrumented smoke, baseline profile present, a canary install-and-launch path green. "CI built the AAB" is not verification; verification is *this specific AAB* observed working. An artifact nobody ran is an unverified cargo load heading to production.

## Incremental Builds <!-- 3 -->
Gradle correctness is paired with **fast incremental builds** (QUALITY-BAR §7): configuration cache and up-to-date checks keep CI and local iteration fast as the build grows, because a build that takes 20 minutes gets run half as often and trusted less. Configuration-cache bugs surface as "works warm, breaks clean", which is why the release pipeline runs at least one clean build per milestone.

## CI Secrets & Environments <!-- 4 -->
Secrets (keystores, service credentials) are **scoped, least-privilege, per-environment** (QUALITY-BAR §4, §7): CI reads them from its secret store, debug builds never see release keys, logs redact them, and nothing secret serializes into the repo or public build files. A release pipeline's leak surface — keystores, tokens, store credentials — is at least as valuable as the app code, and protected as such.
